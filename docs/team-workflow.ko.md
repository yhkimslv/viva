# VIVA 팀 프로젝트 운영 가이드

VIVA는 각 팀원의 컴퓨터에서 변경사항을 검토하고 저장하고 공유하는 도구입니다. 작업 배정과 마감일은 GitHub 이슈나 팀 보드에 기록하고, 코드 검토와 병합은 GitHub Pull Request에서 진행합니다. 리드는 팀원마다 작업 브랜치를 쓰게 하고, 작은 변경 단위로 검토하는 흐름을 먼저 정하세요.

## 첫 프로젝트 연결

1. 팀 저장소 접근 권한과 Git 설치를 확인합니다. 첫 저장을 하기 전에 Git의 이름과 이메일도 설정합니다. GitHub에서 팀 저장소를 한 번 clone하고 로컬 폴더를 준비합니다. VIVA에는 아직 clone이나 Git 사용자 정보를 설정하는 화면이 없습니다.
2. VIVA에서 **Link a Project**로 그 폴더를 연결합니다. `.env`, 인증서, 생성 폴더 경고를 확인하고 필요한 항목을 제외합니다. 이미 추적 중인 파일은 `.gitignore`에 추가해도 이력에서 제거되지 않습니다.
3. **Connect GitHub**에서 각자 본인의 계정으로 로그인합니다. 팀원끼리 토큰을 공유하지 않습니다.
4. **Upload to Cloud → Upload work to a team repository**에서 실제 팀 저장소 remote를 선택합니다. 팀 프로젝트에는 개인 백업 모드 대신 이 대상을 사용합니다.
5. 새 작업 브랜치 이름을 `feature/이름-작업`처럼 정합니다. 첫 업로드 뒤에는 같은 브랜치에 계속 업로드할 수 있습니다.
6. AI를 쓸 경우 팀의 코드 전송 정책을 먼저 확인하고 **Project Settings**에서 해당 프로젝트의 AI 전송 권한을 허용합니다. 일반적인 저장·업로드·병합에는 AI 연결이 필요하지 않습니다.

기존 버전에서 설정한 팀 업로드 대상은 **Project Settings → Change upload target**에서 한 번 다시 선택해야 합니다. VIVA가 확인한 저장소 소유자와 이름을 보관하고, 이후 remote 주소가 바뀌면 다시 확인하도록 하기 위한 절차입니다.

## 매일 작업하기

1. 작업 전 현재 브랜치를 확인합니다. 같은 브랜치의 원격 변경은 **Get Updates**로 커밋 목록을 검토한 뒤 가져옵니다.
2. 파일을 수정하고 변경 목록을 검토합니다. 저장에 포함할 파일을 stage한 뒤, 변경 목적을 설명하는 메시지로 **Save Progress**합니다. 이 단계는 로컬 저장입니다.
3. 팀에 공유할 준비가 되면 **Upload to Cloud**를 누릅니다. 업로드 대상 브랜치를 확인합니다.
4. **Open pull request**로 GitHub 검토 화면을 열고 문제, 변경 결과, 확인 방법을 적습니다. 이 링크는 PR 작성 화면을 열며 PR을 자동 생성하지는 않습니다.
5. 리뷰 의견에 따른 수정도 같은 브랜치에서 저장하고 업로드합니다. 이미 열린 PR에 커밋이 추가됩니다.

**Get Updates는 선택한 작업 브랜치의 원격 변경을 가져옵니다.** 작업 브랜치에 최신 `main`을 반영하려면 변경사항을 먼저 저장하고 `main`으로 전환해 업데이트한 다음, 작업 브랜치로 돌아와 브랜치 메뉴에서 `main`을 병합합니다. 팀 저장소의 기본 브랜치 이름이 다르면 그 이름을 사용합니다.

외부 편집기나 터미널에서 브랜치를 바꾼 뒤 대상 불일치 오류가 보이면, VIVA에서 원하는 브랜치로 전환하거나 업로드 대상을 다시 선택합니다. 오류를 없애려고 기본 브랜치 업로드 모드를 선택할 필요는 없습니다.

## 리드의 리뷰와 병합

GitHub에서 기본 브랜치에 리뷰 승인과 CI 통과 규칙을 설정하는 것을 권장합니다. VIVA의 확인 창은 앱 안의 작업을 보호하므로, 저장소 전체의 협업 규칙은 GitHub에서도 설정하세요.

리뷰에서는 다음을 확인합니다.

- PR 하나가 설명 가능한 작업 단위인지, 담당 이슈와 완료 조건이 연결되어 있는지
- 실제 실행 결과와 필요한 테스트가 있는지
- 비밀키, 개인 설정, 생성 파일이 포함되지 않았는지
- 충돌 해결 과정에서 다른 팀원의 수정이 빠지지 않았는지

승인과 CI 확인 뒤 GitHub에서 병합합니다. 병합한 작업 브랜치를 지우기 전에는 기본 브랜치를 업데이트해 작업이 반영됐는지 확인합니다. VIVA는 현재 브랜치에 합쳐지지 않은 로컬 브랜치 삭제를 거부합니다. squash merge처럼 커밋 해시가 달라지는 병합은 Git의 조상 관계 검사로 확인되지 않을 수 있으므로, 이런 정리는 리드가 GitHub의 병합 기록과 내용을 확인한 뒤 별도로 진행합니다.

## 충돌 해결

충돌 창은 파일마다 **Keep Mine**과 **Keep Theirs**를 제공합니다. 선택은 충돌 구간만이 아니라 **파일 전체**에 적용됩니다. Mine은 현재 브랜치, Theirs는 들어오는 브랜치입니다. 양쪽 수정이 모두 필요하면 창을 열어 둔 채 편집기에서 내용을 합치고 stage하세요. 창을 먼저 닫았다면 일반 저장 화면에서 staged 변경을 검토하고 commit하여 병합을 마칠 수 있습니다.

파일을 모두 해결해도 병합은 아직 끝나지 않습니다. 결과를 실행해 확인하고 메시지를 입력한 뒤 **Complete merge**를 누릅니다. 저장이 실패하면 창이 열린 상태로 남으므로 오류를 확인하고 다시 시도할 수 있습니다. 병합을 중단하려면 **Abort merge**를 사용합니다.

현재 앱의 충돌 흐름은 merge를 기준으로 합니다. rebase·cherry-pick 충돌, binary 파일과 삭제가 섞인 충돌은 리드와 함께 Git 상태를 확인하고 처리하세요.

## 주간 진행 확인

**Weekly Report**는 현재 로컬 브랜치에서 도달 가능한 이력을 기준으로 집계합니다. 모든 팀원의 열린 PR, 미업로드 작업, 다른 브랜치를 모은 대시보드는 아닙니다. 주간 회의에서는 각 작업의 완료 조건과 데모, GitHub의 열린 PR, 막힌 문제를 함께 확인하세요. 커밋 수와 변경 줄 수는 개인 성과 점수로 사용하지 않습니다.

## VIVA 개발 확인

Node.js 24 환경에서 의존성을 설치한 뒤 다음을 실행합니다.

```sh
npm ci
npm run typecheck
npm test
npm run build
npm run dev
```

타입 검사·테스트·프로덕션 빌드는 CI에서도 실행합니다. 배포 파일을 만들기 전에는 실제 대상 OS에서 로그인, 연결, 저장, 두 번 연속 업로드, 업데이트, 충돌 해결을 시험하세요.
